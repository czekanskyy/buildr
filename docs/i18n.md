# Localization (i18n)

See also [ADR-023](adr/ADR-023-localization.md). Localization ships in the MVP, not deferred.

## Model: shared structure, localized content

| Layer | Locale-dependent? | Mechanism |
|---|---|---|
| Structure (nodes, slots) | No | One document serves every language |
| Styles, tokens | No | Shared (RTL is out of MVP scope) |
| `localizable` static props | Yes | `StaticValue.l10n[locale]`; `value` is the default-locale value |
| Text templates (`mode: 'template'`) | Yes | `ExpressionValue.l10n[locale]` — a per-locale template source |
| Bindings / formulas | Content yes, definition no | Data is fetched from the CMS in the active locale (Payload field localization); the same binding path is used for every language |
| Built-in component strings ("opens in a new tab", "Next page", form messages) | Yes | A `messages` catalog per locale in `@next-buildr/components` (`en`, `pl`), overridable in configuration, delivered through `env.messages` (serializable, so it also works in client components) |

- **Configuration**: `LocaleConfig { locales: LocaleCode[]; default: LocaleCode; fallback: boolean; intl: Record<LocaleCode, string> }`. In the Payload integration this comes from `config.localization`; in the playground, from the application's own configuration.
- **`PropDef.localizable`** defaults to `true` for `text`, `textarea`, `richText`, `link`, and accessibility text props (`alt`, `ariaLabel`, `label`); `false` for `number`, `boolean`, `select`, `icon`, `media` (the image itself is shared; its `alt` text is what gets translated).
- **Resolution**: see step 1 in [dynamic-bindings.md](dynamic-bindings.md#resolution). Formatters (`formatDate`, `formatCurrency`, `plural`) use `intl[ctx.locale]`.
- **Commands**: `node.setProp { id, prop, value, locale? }`. When `locale` differs from the default locale, the write lands in `l10n[locale]` (only valid for `StaticValue` and template-mode `ExpressionValue`). `node.unsetProp { id, prop, locale? }` removes a translation.
- **Validation**: `l10n` keys must belong to `LocaleConfig.locales` (an unknown key is a warning, but is preserved); values pass the prop's own kind validator. A `missing-translation` rule (severity `info`) flags `localizable` props with no translation for a given language.
- **Editor**: a locale switcher lives in the toolbar. In a non-default language, fields show the default-locale value greyed out with a "Translate" action. Inline editing writes to the current language. A banner reminds the author that structural and style edits apply to every language. The Issues panel groups missing translations per language. The canvas renders the selected language (`locale` is part of `editor:init` / `locale:set`), and the data context is fetched in that language.
- **Payload**: `layout` is **not** a `localized` field, because translations live inside the AST itself. Business fields (`title`, `slug`, `excerpt`, `meta`, `content`, media `alt`) are `localized`. Endpoints accept a `locale` parameter (mapped to Local API's `locale` + `fallbackLocale`). Publishing covers the document across every language at once (Payload's own draft model).
- **Next.js**: routes carry a `[locale]` segment, `BuildrPage` receives `locale`, `generateStaticParams` runs per locale, and `buildrMetadata` generates `alternates.languages` (hreflang). Internal links are `localizable` props, so each language can point at its own URL.
- **Future, additive extensions**: per-language layouts as an opt-in plugin option (`localized: true` on the `layout` field, v0.3), RTL support (v0.3), per-language publish status (once Payload's own model supports it well).
