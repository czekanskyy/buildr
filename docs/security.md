# Security model

See also [ADR-016](adr/ADR-016-security-model.md).

| Threat | Mitigation |
|---|---|
| XSS via props / bindings / CMS data | React escapes text. `dangerouslySetInnerHTML` is forbidden (linted) outside an audited, isolated code path (a v0.3 sandboxed embed). Values sourced from bindings go through the same validation and sanitization as static values. |
| Malicious URLs | `sanitizeUrl`: allows `http:`, `https:`, `mailto:`, `tel:`, relative paths, `#anchor`. Blocks `javascript:`, `data:`, `vbscript:`, unknown schemes, and obfuscation (control characters, entities). Applies to `link`/`media` props and to rich text. |
| Rich text | A JSON walker with an allowlist of node types. No raw HTML. Links are sanitized. |
| CSS injection | A per-property value grammar (no `url()`, `;`, `}`, `@`, `\`), an allowlisted token name set, a validated theme. The compiler only ever emits already-validated values. |
| HTML embeds | Out of MVP. In v0.3: an `Embed` component with an **allowlisted provider set** (YouTube, Vimeo, Maps, Spotify, ...). The user supplies a URL; the `src` is built from the provider's own template, with `sandbox`, minimal `allow`, `referrerpolicy`, and `loading=lazy`. |
| Custom HTML / custom JS | **Not in MVP.** The v0.3 safer model: "Custom HTML" only inside a `srcdoc` iframe with `sandbox="allow-scripts"` (no `allow-same-origin`, so it runs with an opaque origin, no cookie/DOM access to the parent), auto-height via postMessage, gated behind an `unsafeEmbed` permission restricted to the admin role. Custom JS/React is instead added by a developer as a **registered component** (code-reviewed, typed) — never authorable from inside the editor. |
| Expression execution | No `eval`/`Function`, an allowlisted function set, no prototype or host-object access, step/size limits, no regex. |
| Untrusted JSON (database, clipboard, postMessage, API) | Zod validation of the envelope plus limits, invariants, and per-component prop validation at every boundary. Unknown fields are preserved but never rendered. Parsing enforces a size limit. |
| Authorization | Every endpoint requires a Payload user. Local API calls always use `overrideAccess: false`. `edit`/`publish`/`unlockTemplates` permissions are enforced server-side. |
| Tenant boundaries | Payload's own access control (including its multi-tenant plugin) applies to every operation, including `QuerySpec` execution against documents. Production-time queries run with the **viewer's** permissions (public read), never the author's. Collections and fields exposed to `QuerySpec` are explicitly allowlisted (`queryable`). |
| Data leakage via bindings | `DataSchema` acts as an allowlist. `users` is never a context scope (only `authors`). Hidden/sensitive fields are excluded. |
| Preview endpoints | Require an authenticated user. Redirects only target relative paths. Canvas and preview responses: `Cache-Control: private, no-store`, `noindex`. Draft mode is gated behind authentication. |
| postMessage | `targetOrigin` is always a concrete value, never `'*'`. Both sides verify `event.origin` (allowlisted), `event.source === iframe.contentWindow`, a session nonce, and message schema/version. Malformed messages are dropped. |
| Iframe / clickjacking | The canvas route sends `frame-ancestors` set to the editor's origin. The editor route sends `frame-ancestors 'none'`. The canvas route itself requires authentication. |
| CSRF | Payload's own `csrf` origin allowlist. Mutating requests require `Content-Type: application/json` and an `Origin` check. |
| Denial of service | Document limits, `limit <= 50` on queries, no nested Loop queries, expression evaluation budgets, form submission rate limiting. |
| Forms | The field schema is derived server-side from the **published** document (never trusted from the client), with type/length validation, a honeypot field, IP-hash rate limiting, and an allowlisted notification-recipient set. An optional Turnstile challenge is verified on the server and fails closed (see [Captcha](#captcha-turnstile)). |
| Supply chain | pnpm lockfile, `allowBuilds`, Renovate, npm publish with provenance (OIDC), 2FA/Trusted Publishing, CodeQL. |

## Provider embeds (Map)

`buildr/map` ([ADR-029](adr/ADR-029-provider-embeds-and-form-challenges.md)) embeds the Google Maps Embed API. It is off until the host sets `Platform.maps`. Hosts that turn it on must do the following.

- **CSP.** If your CSP restricts frames (`frame-src` or `default-src`), add `https://www.google.com` to it, and only when a key is configured; without a key the block renders a link and loads nothing. Do not add a new `frame-src` line to a CSP that has none: it would block every other frame, such as `buildr/iframe` hosts. If your CSP does not restrict frames, nothing is needed.
- **Key restriction.** The Maps Embed API key is public: it is in the page HTML and RSC data (the frame URL). Restrict it in Google Cloud to the Maps Embed API and by HTTP referrer. List every site origin as `https://<site-origin>/*`, and the editor preview origin if the preview should show the map. An unrestricted key can be copied and used by anyone. The frame sends `referrerpolicy="strict-origin"`, so Google sees the origin only, never the path.
- **Consent and GDPR.** Click-to-load is on by default. Until the visitor clicks, nothing reaches Google. After the click Google receives the visitor's IP address, user agent and the site origin, and any cookies Google already has in that browser, which may identify a signed-in Google user (the frame has `allow-same-origin`, and browsers that allow third-party cookies send them). Google may also store data in its frame. The fixed notice before the click mentions the IP address and stored data only, so the host's privacy policy must describe the rest. The notice before the click is the fixed catalog text; authors cannot change it. The host is the controller and must name Google in its privacy policy. Buildr remembers no consent. A host that sets `clickToLoad: false` is responsible for consent before the page renders. If that depends on a per-visitor decision, use a per-request `Platform` and dynamic, uncached rendering: a static or ISR page would cache the iframe and serve it to visitors who never consented.
- **`iframeHosts`.** The frame URL is checked against `capabilities.iframeHosts`. A host that sets the list must include `www.google.com`, or the map falls back to the link.
- **`buildr/iframe` is unchanged.** It keeps `sandbox="allow-scripts"` and `referrerpolicy="no-referrer"`. The Map sandbox (`allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox`) applies only to the constant Google origin, which the author cannot change, so the frame is never the site's own origin. The configuration does trust Google with unsandboxed popups; only the initial `src` is validated.
- **Canvas.** The editor canvas never loads a provider and never receives the key.

Known limit: the exact sandbox together with `strict-origin` has not been checked against Google with a real, referrer-restricted key. Check it once before relying on it. If it fails, the fix is a new ADR, not an ad-hoc sandbox token.

## Captcha (Turnstile)

`buildr/captcha` ([ADR-029](adr/ADR-029-provider-embeds-and-form-challenges.md)) adds a Cloudflare Turnstile challenge to a form. It is off until the host sets `Platform.captcha` (site key) and `forms.captcha` plus `forms.clientIp` in the Payload plugin (secret key). Setup: [nextjs.md](nextjs.md#captcha-pb-160d), [payload.md](payload.md#captcha-pb-160d).

**What it protects, and what it does not.**

- It raises the cost of scripted and bulk submissions to a form endpoint: spam in the submissions collection, mail to `notifyTo`, and rate-limit exhaustion. It is a second layer after the honeypot, not a replacement for the per-form limiter, which keeps running.
- The server decides from the *published* form whether a challenge is required, and checks the token, the hostname, the action and a per-form `cData` binding against Cloudflare. A token cannot be replayed (single use) or moved to another form or another host.
- It does not stop a person, a paid solving service or a browser Turnstile accepts. It does not protect reads, and it protects only the Payload form endpoint: a function-valued form action ([nextjs.md](nextjs.md#captcha-pb-160d)) must verify the token itself.
- It fails closed. With no JavaScript, a blocked provider script, a Cloudflare outage or a missing server config, the form cannot be submitted (`503`, nothing stored or mailed). This is accepted, and the block shows a notice.
- Pages that inherit one template share its form's `cData` by design; the token is still single use and still tied to your hostnames.

**Secrets.** The site key is public. The secret key lives only in the host's environment and the `forms.captcha.secretKey` option, read in `payload.config.ts` through `process.env`; it must never be in the document, the manifest, client props, the platform, the Next config's `env` or a `NEXT_PUBLIC_*` variable. Plugin init errors and logs never print it, and logs never carry the token or Cloudflare's raw answer. The token is stripped before validation and is never stored or emailed.

**Trusted client address.** The per-IP limiter and the concurrency cap exist to protect the call to Cloudflare, and they trust `forms.clientIp`. The proxy must overwrite that header and the origin must not be reachable directly; a configured source never falls back to `X-Forwarded-For`. IPv6 clients share a bucket per /64 prefix, IPv4-mapped IPv6 counts as IPv4, and zone ids or invalid values share one `unknown` bucket. The captcha per-IP limiter is its own instance and fails closed (`429` for new keys) when full instead of evicting live counters. Residual risk: a flood across many distinct IPv6 /64 prefixes can fill the in-memory limiter, and new visitors then get `429` until entries expire. That is a denial of service of the captcha form only, never a bypass; on a multi-instance or serverless host the mitigation is a shared `forms.rateLimiter` store (it also serves the captcha counter, under `captcha:`-prefixed keys). See [payload.md](payload.md#captcha-pb-160d).

**Consent and GDPR.** Loading the widget sends the visitor's IP address and browser signals to Cloudflare, and Cloudflare may set cookies or storage. Click-to-load is on by default: nothing is requested from `challenges.cloudflare.com` until the visitor presses "Load the check" (the notice says what will be processed), and Buildr remembers nothing (no cookie, no storage). The host is the controller and must name Cloudflare in its privacy policy; the fixed notice does not replace that. A host that sets `clickToLoad: false` must ensure consent before the page renders; if that is per visitor, use a per-request `Platform` with dynamic, uncached rendering, because the Next config is created once and a static or ISR page would load the widget for everyone. The server-side `siteverify` call sends only the secret and the token, never the visitor's address.

**CSP.** If your CSP restricts scripts or frames, add `https://challenges.cloudflare.com` to `script-src` and `frame-src`, and allow outbound HTTPS from the server to that host. Add it only when the captcha is on. A new `frame-src` or `script-src` directive restricts everything it does not list, so adding one to a CSP that has none blocks every other iframe or script source. The example app does exactly this for frames: its public-page CSP otherwise has only `frame-ancestors`, and it adds a `frame-src` listing just the Turnstile host (when the site key is set) and the Google Maps host (when the map key is set). Any other iframe on its public routes must be added to `frame-src` in `next.config.ts`. A host that already restricts frames just merges the host into its existing directive.

- **Nonce.** With a nonce-based `script-src`, the injected loader script needs your page's nonce. The enhancer copies the first non-empty `nonce` of any `script[nonce]` element on the page, and otherwise the `content` of `<meta name="csp-nonce">`. Provide at least one carrier, for example by rendering the meta tag next to the nonce your framework already uses. Without a nonce the script is blocked and the form fails closed.
- **Host allowlist is not a nonce policy.** The Cloudflare host in a source list lets the browser run any script from that host, with or without a nonce, so an allowlist alone gives no nonce enforcement. A strict policy puts the nonce plus the Cloudflare host in `script-src-elem` (or `script-src`) and keeps the nonce carrier available. If the element policy lists only the nonce and no Cloudflare host, as the playground e2e does to test the worst case, the loader works only when a carrier exists. With `missing` the script is blocked and the form fails closed. The carriers, in order: the first non-empty `script[nonce]` on the page, else `<meta name="csp-nonce">`. The e2e covers the `script`, `meta` and `missing` carriers; it uses no `'strict-dynamic'`.
- **Example.** `script-src-elem 'self' 'nonce-…' https://challenges.cloudflare.com; frame-src https://challenges.cloudflare.com` (merge into your existing directives; a map's `https://www.google.com` goes in the same `frame-src`).
- **Provider script.** It runs with the page's own origin and power, and there is no SRI because Cloudflare updates it. Isolate the admin on a separate origin with host-only session cookies and server-enforced CSRF and `Origin` checks: a compromised provider script on a shared origin could make credentialed Payload requests whenever an editor opens the page. Click-to-load protects visitors only until the click.

**Canvas and preview.** The editor canvas never loads the provider: it renders a neutral hint only, does not read `Platform.captcha`, and must not be given it. The preview loads the provider but always requires the click, even if the host set `clickToLoad: false`, so reviewing a draft never contacts Cloudflare silently. The canvas also marks a second captcha in the same form.

See also [payload.md](payload.md#authentication-and-authorization) for the concrete access-control implementation, and [editor.md](editor.md#the-postmessage-protocol) for the protocol's own security details.
